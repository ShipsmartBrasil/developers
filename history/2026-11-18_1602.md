## 2. Passo a passo do processo

### Passo 1 — Ler as instruções do projeto
Reler o `AGENTS.md` por completo **antes de qualquer coisa**. Ele define:
- a lista de tópicos obrigatórios do guia;
- o que **nunca** pode ser publicado;
- a estrutura de pastas e a regra dos nomes de arquivo em pt-br;
- o idioma-fonte e os idiomas de tradução.

### Passo 2 — Mapear a superfície pública da API
Levantar a lista completa de endpoints públicos, por versão, com método e rota.
Para cada endpoint, identificar:
- a operação que ele representa no fluxo de negócio;
- se é síncrono ou assíncrono;
- se depende de outro endpoint (ex.: precisa de uma cotação válida antes).

Fontes a cruzar **sempre as duas**:
1. a documentação interativa publicada em `/doc` (contrato publicado);
2. o comportamento real da API (regras efetivamente aplicadas na requisição).

> **Esse cruzamento é o passo mais importante.** Nesta atualização foram encontradas várias
> divergências entre o contrato publicado e o comportamento real (campos obrigatórios diferentes,
> limites de tamanho diferentes, campos existentes mas não documentados, endpoints não documentados).
> Quando houver divergência, **documentar o comportamento real** e, se a divergência for um defeito,
> reportá-la a quem mantém a API.

### Passo 3 — Extrair os dados de cada campo
Para cada endpoint, montar a tabela de parâmetros com:
- nome do campo (inclusive aninhado, com notação de ponto);
- localização (`body`, `query`, `path`, `header`);
- tipo;
- obrigatoriedade — incluindo obrigatoriedade **condicional** (“obrigatório quando X não for enviado”);
- tamanho/valor mínimo e máximo;
- valor padrão, quando houver;
- lista de valores aceitos, quando for enumerado;
- descrição funcional.

Levantar também, por endpoint:
- exemplo de resposta de sucesso e o significado de cada campo retornado;
- a lista de códigos HTTP possíveis;
- as mensagens de erro reais, com a causa e a correção de cada uma;
- as regras de negócio que podem bloquear a operação.

### Passo 4 — Escrever a versão pt-br
pt-br é a **fonte de verdade**. Escrever todas as páginas aqui primeiro e só depois traduzir.
Seguir o template da seção 3 deste documento.

### Passo 5 — Validar a versão pt-br
Rodar a verificação automatizada (seção 4) ainda **antes** de traduzir. Corrigir tudo no pt-br,
porque qualquer erro estrutural se multiplica por 4 na tradução.

### Passo 6 — Traduzir
Traduzir pt-br → en-us, es-es, fr-fr, it-it, um idioma por vez (podem ser paralelos).
Cada tradução recebe:
- o conjunto completo de arquivos pt-br;
- a regra de **paridade estrutural** (seção 3);
- a lista do que traduzir e do que manter idêntico (seção 3);
- o glossário de terminologia daquele idioma;
- a regra de recálculo de âncoras (seção 3).

### Passo 7 — Validar tudo
Rodar a verificação automatizada nos 5 idiomas e no README principal.
Nenhum erro pode restar.

### Passo 8 — Registrar
Criar um novo arquivo em `history/` com a data/hora da atualização, descrevendo o que mudou e
deixando as pendências anotadas para a próxima rodada.

## 3. Convenções de escrita

### Template de página
Toda página de endpoint segue esta ordem de seções:

1. `# Título`
2. Link de volta ao README do idioma + pré-requisitos
3. `## Visão geral` — o que o módulo faz, em 3 a 5 bullets
4. `## Base URL` — produção, homologação e documentação interativa
5. `## Autenticação` — bloco de headers
6. `## Fluxo de uso` — passo a passo numerado, com diagrama ASCII quando ajudar
7. `## Conceitos essenciais` — tabelas explicando os enums do domínio (quando aplicável)
8. `## Endpoint: <ação>` — um por operação, contendo:
   - método e rota, e quando usar
   - `### Parâmetros` (uma subseção por objeto do payload)
   - `### Payload mínimo`
   - `### Payload máximo`
   - `### Exemplo de request` (`curl`)
   - `### Exemplo de response`
   - `### Campos da resposta`
9. `## Regras de negócio`
10. `## Erros comuns` — tabela status / significado / como corrigir
11. `## Observações finais` — links para as páginas relacionadas

### Regras de conteúdo
- **Nunca** mencionar ou dar pistas da tecnologia usada na API.
- **Nunca** publicar nada sobre a API de backend.
- Domínio público sempre `https://api.shipsmart.global`; documentação em `/doc`.
- Homologação sempre `https://hmlapi.shipsmart.com.br`, documentação em `/doc`.
- Deixar explícito que **todos os exemplos são meramente ilustrativos e não contêm dados válidos**.
- Payload mínimo = o menor payload realmente aceito. Payload máximo = todos os campos aceitos.
- Sempre que a API tiver duas formas de informar a mesma coisa (ex.: por código cadastrado ou por
  campos manuais), documentar as duas como “Forma A / Forma B” e avisar para não misturar.
- Erros: usar a mensagem real da API, não uma paráfrase.
- Preferir tabelas a parágrafos longos.
- Repetir informação entre páginas só quando ela for crítica; nos outros casos, linkar.

### Paridade estrutural entre idiomas
Cada arquivo traduzido precisa ter, em relação ao pt-br:
- o mesmo número de títulos, nos mesmos níveis e na mesma ordem;
- as mesmas tabelas, com o mesmo número de colunas e linhas, na mesma ordem;
- os mesmos blocos de código;
- os mesmos blocos de citação, nas mesmas posições.

Nada de adicionar, remover, juntar, reordenar ou resumir seções.

### O que traduzir
Títulos, texto corrido, listas, citações, cabeçalhos e células explicativas de tabela, rótulos dentro
de diagramas, textos de link e os dados de exemplo legíveis por humanos (nomes, endereços, descrições).

### O que manter idêntico
- Chaves e valores enumerados de JSON, códigos de moeda e de país, UUIDs, trechos de base64
- Nomes de campo da API, em qualquer lugar que apareçam
- Métodos HTTP, rotas, query strings e códigos de status
- Comandos `curl`
- Nomes de header e seus valores
- Códigos e chaves de status retornados pela API
- Valores de filtro e chaves de documentos
- **As mensagens literais que a API retorna** — reproduzidas no idioma padrão da API, para que o
  integrador consiga casar a string exata. A explicação ao lado é que é traduzida.
- Nomes de arquivo nos links (permanecem em pt-br)

### Dados de exemplo
- Manter **sem acentuação**, para parecerem dados reais de payload.
- Deixar claro na página que são ilustrativos.
- Nunca usar dado real de cliente, documento fiscal válido ou token real.
- Placeholder de token por idioma: `SEU_TOKEN`, `YOUR_TOKEN`, `SU_TOKEN`, `VOTRE_TOKEN`, `IL_TUO_TOKEN`.

### Âncoras de link
Ao traduzir um título, a âncora que aponta para ele **precisa ser recalculada**.
Regra de slug: remover crases e pontuação (incluindo `—`, `(`, `)`, `[`, `]`, `:`, `/`, `,`, `.`, `'`),
passar para minúsculas e trocar espaço por `-`. Acentos são preservados.
Atenção: um travessão entre espaços produz **hífen duplo** — `Parâmetros — boxes[]` → `parâmetros--boxes`.

## 4. Verificação automatizada

Rodar na raiz do repositório. Checa, nos 5 idiomas e no README principal:
links de arquivo, âncoras, paridade estrutural, arquivos faltando/sobrando, a URL correta da
documentação e vazamento de termos de tecnologia.

````python
import os, re, unicodedata, glob

def slug(h):
    h = h.strip().lower().replace('`', '')
    keep = [c for c in h if c.isalnum() or c in '-_ ' or unicodedata.category(c).startswith('M')]
    return ''.join(keep).strip().replace(' ', '-')

def heads(f):
    return {slug(m.group(1))
            for m in (re.match(r'^#{1,6}\s+(.*)$', l) for l in open(f).read().splitlines()) if m}

def stats(f):
    t = open(f).read()
    return (len(re.findall(r'^#{1,6}\s', t, re.M)),   # títulos
            len(re.findall(r'^\|', t, re.M)),          # linhas de tabela
            t.count('```'),                            # blocos de código
            len(re.findall(r'^>\s', t, re.M)))         # citações

LANGS = ['pt-br', 'en-us', 'es-es', 'fr-fr', 'it-it']
src = {os.path.basename(f): f for f in glob.glob('pt-br/*.md')}
errs = []

for folder in LANGS:
    files = sorted(glob.glob(f'{folder}/*.md'))
    H = {f: heads(f) for f in files}
    for f in files:
        for m in re.finditer(r'\]\(([^)]+)\)', open(f).read()):
            link = m.group(1)
            if link.startswith(('http', 'mailto:')):
                continue
            path, _, anchor = link.partition('#')
            target = os.path.normpath(os.path.join(os.path.dirname(f), path)) if path else f
            if not os.path.exists(target):
                errs.append(f'{f}: ARQUIVO INEXISTENTE -> {link}')
                continue
            if anchor:
                H.setdefault(target, heads(target))
                if anchor not in H[target]:
                    errs.append(f'{f}: ANCORA INEXISTENTE -> {link}')
    if folder != 'pt-br':
        for name, pf in sorted(src.items()):
            tf = f'{folder}/{name}'
            if not os.path.exists(tf):
                errs.append(f'{folder}: FALTA {name}')
            elif stats(pf) != stats(tf):
                errs.append(f'{folder}/{name}: PARIDADE pt{stats(pf)} vs {stats(tf)}')
        extra = {os.path.basename(f) for f in glob.glob(f'{folder}/*.md')} - set(src)
        if extra:
            errs.append(f'{folder}: ARQUIVO SOBRANDO {extra}')

for m in re.finditer(r'\]\(([^)]+)\)', open('README.md').read()):
    link = m.group(1)
    if not link.startswith(('http', 'mailto:')) and not os.path.exists(link.split('#')[0]):
        errs.append(f'README.md: ARQUIVO INEXISTENTE -> {link}')

todos = [f for lang in LANGS for f in glob.glob(f'{lang}/*.md')] + ['README.md']

ruim = [f for f in todos if 'shipsmart.global/docs' in open(f).read()]
if ruim:
    errs.append(f'URL DE DOC ERRADA (/docs em vez de /doc): {ruim}')

# A lista de termos proibidos NAO fica versionada: ela mora em `.termos-proibidos`
# (um termo por linha, arquivo listado no .gitignore), justamente para nao dar a pista
# que o guia precisa esconder. Mantenha esse arquivo fora do repositorio publico.
termos = []
if os.path.exists('.termos-proibidos'):
    termos = [l.strip() for l in open('.termos-proibidos') if l.strip()]
else:
    errs.append('AVISO: .termos-proibidos nao encontrado - checagem de vazamento NAO executada')

vaz = [f'{f}: {kw}' for f in todos for kw in termos
       if re.search(r'\b' + re.escape(kw) + r'\b', open(f).read())]
if vaz:
    errs.append('VAZAMENTO DE TECNOLOGIA: ' + '; '.join(sorted(set(vaz))))

print('\n'.join(errs) if errs else 'OK: links, ancoras, paridade, URLs e sem vazamento')
````

## 5. Armadilhas encontradas nesta rodada

Pontos que custaram tempo e que valem ser conferidos de novo na próxima atualização:

1. **Contrato publicado ≠ comportamento real.** Vários campos tinham limites de tamanho e
   obrigatoriedade diferentes dos documentados. Sempre cruzar as duas fontes.
2. **Endpoints não documentados.** Havia operação pública sem nenhuma documentação. Conferir a lista
   de rotas inteira, não só o que aparece em `/doc`.
3. **Ambiguidade de rota.** Uma rota de cancelamento com dois segmentos conflita com a de um
   segmento. Isso precisa de aviso explícito no guia.
4. **Operações assíncronas sem validação na resposta.** Alguns cadastros respondem sucesso e
   descartam registros inválidos depois, em silêncio. Isso tem que estar destacado, com a tabela
   completa das regras aplicadas no processamento.
5. **Divergência de nome entre request e response.** Existe campo que entra com um nome e volta com
   outro. Documentar o par, com aviso.
6. **Valores legados.** Existem valores aceitos apenas por compatibilidade e convertidos
   internamente. Documentar, mas orientar a não usar em integrações novas.
7. **Âncoras após tradução.** Foi a principal fonte de link quebrado. Validar sempre com o script.
8. **Apóstrofo em dado de exemplo.** Em francês e italiano, um apóstrofo dentro do `--data '...'`
   quebra o `curl`. Manter os dados de exemplo sem apóstrofo.
9. **Diagramas ASCII.** Ao traduzir, o alinhamento das colunas se perde. Reavaliar o padding.
