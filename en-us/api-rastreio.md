# Shipment Tracking

- [Back to the language README](README.md)
- Prerequisite: [Getting Started](api-primeiros-passos.md)

> ⚠️ **Examples are for illustration only:** all payloads, responses, identifiers, codes, documents and tokens
> on this page are fictitious and **are not valid data**. Replace them with the real data of your account and your operation.

## Overview
- Queries the operational status and the history of a shipment, from its receipt on the platform until
  delivery (or cancellation).
- The same response brings **three views**: the chronological `timeline`, the events **grouped by status** and the
  **latest state** (`last_update`).
- There are two ways to query: by the shipment identifier (`{shipping}`) or by the identifier of your
  sales channel (`channel_identifier_number` + `channel_code`).
- Works for shipments created in **v1 and v2** (the tracking routes exist only in v1).

## Base URL
- Production: `https://api.shipsmart.global`
- Staging: `https://hmlapi.shipsmart.com.br`
- Interactive documentation: `https://api.shipsmart.global/doc` and `https://hmlapi.shipsmart.com.br/doc`

## Authentication
```
Authorization: Bearer YOUR_TOKEN
lang: pt
```

| Header | Required | Values | Default | Note |
|---|---|---|---|---|
| `Authorization` | **yes** | `Bearer <token>` | - | Token of your account. The profile needs the shipment status query permission |
| `lang` | no | `pt`, `en`, `es` | `pt` | Language of the messages and of the descriptions generated by the platform |

> The `lang` header translates the response `message` and the descriptions of the events generated by the **platform**
> (receipt, payment, processing, cancellation and error). The descriptions of events coming from the
> **carrier** are returned as the carrier sent them and do **not** change with the language.
> The codes (`status_code`) and the group keys never change with the language — use them in your integration logic.

## Usage flow
1. Create the shipment ([Shipment v1](api-remessa-v1.md) or [Shipment v2](api-remessa-v2.md)) and store the `quotation`
   (UUID) used in the creation.
2. Query the status by `{shipping}` (recommended) or by the channel identifier.
3. When the `shipped` group appears, the documents already exist: download them in [Shipment Documents](api-documentos.md).
4. Keep querying at longer intervals to follow pickup, transit and delivery.
5. Stop querying when `last_update` indicates a final state (see [Polling best practices](#polling-best-practices)).

```
create shipment ──► GET .../status ──► (shipped?) ──► GET .../docs
                          │                 │
                          │ no              │ yes
                          ▼                 ▼
                   wait and retry      follow pickup → transit → delivery
```

## Key concepts

### The three views of the response

| View | Where it is | What it contains | Use it to |
|---|---|---|---|
| Chronological | `data.carrier.timeline` | All the events built by the platform and all the carrier tracking events, in the order in which they were recorded | Display the complete history to the end user |
| Grouped by status | `data.received`, `data.shipped`, `data.in_transit`... | One key per status already reached. Each key is a list with **a single event**: the most recent one of that status | Check whether the shipment **has already gone through** a given stage |
| Latest state | `data.last_update` | The current state, in the format `{ "<group>": { ...event } }` | Dashboards and synchronizations: a single read answers "where is the shipment" |

> **Attention:** the groups do not keep the history. If the carrier sends three `in_transit` events, the
> `data.in_transit` group will bring only the last one; all three appear in `data.carrier.timeline`.

### Status groups and codes

| Group (key) | Platform `status_code` | Meaning | Where it can appear |
|---|---|---|---|
| `received` | `RCV0001` | The shipment was received on the platform | Group and `timeline` (always present) |
| `processing_payment` | `PPY0001` | Payment not yet approved (it is also the event displayed for billed payment, `billed`) | Group and `timeline` |
| `paid_out` | `POT0001` | Payment approved by the payment provider | Group and `timeline` |
| `pending_consolidation` | `PCD0001` | Awaiting consolidation (contracts with consolidation) | Reserved (see [Business rules](#business-rules)) |
| `consolidating` | `CDT0001` | Being consolidated | Reserved (see [Business rules](#business-rules)) |
| `processing_shipment` | `PSH0001` | Payment resolved, awaiting processing at the carrier | Group and `timeline` |
| `shipped` | `SPD0001` | **Processed at the carrier. Documents available** | Group and `timeline` |
| `collecting` | `CLG0001` | Carrier on the way to pick up | Group, `timeline` and `last_update` |
| `collected` | `CLD0001` | Picked up by the carrier | Group, `timeline` and `last_update` |
| `in_transit` | `ITR0001` | In transit | Group, `timeline` and `last_update` |
| `delivering` | `DLG0001` | Out for delivery | Group, `timeline` and `last_update` |
| `delivered` | `DLD0001` | Delivered | Group, `timeline` and `last_update` |
| `error` | `ERR0001` | It was not possible to complete the shipment | Only `last_update` |
| `cancelling` | `CCG0001` | Cancellation requested, being processed | Only `last_update` |
| `cancelled` | `CCD0001` | Cancelled | Only `last_update` |
| `foc` | `FOC0001` | Finalized by the carrier | Only `last_update` |
| `eol` | `EOL0001` | End of the tracking life cycle | Only `last_update` |

> **`status_code` is not always an `XXX0001` code.** It brings the raw code from the event source when
> that code exists:
>
> - in the payment event: the status reported by the payment provider (e.g., `approved`);
> - in the tracking events: the carrier own code.
>
> The `XXX0001` codes are used when there is no external code. For business logic, use the **group
> key** (`shipped`, `in_transit`, `delivered`, `cancelled`...) instead of the `status_code`.

### Descriptions generated by the platform

Literal messages in `pt` (they change according to `lang`):

| Group | `status_description` |
|---|---|
| `received` | `Remessa foi recebida em nosso sistema` |
| `processing_payment` | `Aguardando a finalização do processamento do pagamento junto ao gateway: :description ` |
| `paid_out` | `Pagamento aprovado junto ao gateway: :description ` |
| `processing_shipment` | `Remessa esta sendo processada no transportador especificado!` |
| `shipped` | `Remessa foi processada no transportador especificado. Documentos gerados e já disponíveis para download via portal ou API!` |
| `cancelling` (in `last_update`) | `Cancelando Remessa` |
| `cancelled` (in `last_update`) | `Remessa Cancelada` |
| `error` (in `last_update`) | `Não foi possível concluir o embarque desta remessa.` |

> In the payment messages, `:description` is the description sent by the payment provider or, if there is none,
> the platform code itself (`PPY0001` / `POT0001`). Both messages end with a **space** —
> take this into account if you compare strings (the recommendation is not to compare descriptions).

### Typical state flow

```
received
   │
   ├── processing_payment ──► paid_out          (payment via gateway)
   │
   ├── processing_payment                       (billed payment: goes straight on)
   │
   ▼
processing_shipment
   │
   ▼
shipped                 ◄── documents available from here on
   │
   ▼
collecting ──► collected ──► in_transit ──► delivering ──► delivered

States displayed only in last_update:
   error | cancelling ──► cancelled | foc | eol
```

## Endpoint: query status by shipment

- **Method and route:** `GET /v1/shipping/{shipping}/status`
- **When to use:** this is the recommended way. Use the quotation UUID that you sent as `quotation` when creating the shipment.

### Parameters

| Name | Location | Type | Required | Size | Default | Description |
|---|---|---|---|---|---|---|
| `shipping` | path | string | **yes** | - | - | **Form A:** UUID of the quotation used in the shipment. **Form B:** tracking number (AWB) of the shipment |

> **Identifiers accepted in this route:** quotation UUID or AWB. If the AWB is in more than one shipment,
> the most recent one is considered. **The NF-e key is not accepted in this route** (the query responds
> `400`), although it is accepted in the documents route.

### Minimum payload

Endpoint without a body. The path parameter is enough:

```
GET /v1/shipping/9c06fd75-d5f4-40eb-a1a8-f12086f49944/status
```

### Maximum payload

There are no query parameters. The maximum form is the same as the minimum one, varying only the identifier:

```
GET /v1/shipping/9c06fd75-d5f4-40eb-a1a8-f12086f49944/status
GET /v1/shipping/1234567890123/status
```

### Request example

```bash
curl --request GET \
  --url https://api.shipsmart.global/v1/shipping/9c06fd75-d5f4-40eb-a1a8-f12086f49944/status \
  --header 'Authorization: Bearer YOUR_TOKEN' \
  --header 'lang: pt'
```

### Response fields

| Field | Type | Presence | Description |
|---|---|---|---|
| `status` | string | always | `success`, `warning` or `error` |
| `message` | string | always | Message translated by the `lang` header |
| `data.carrier.name` | string | always | Name of the contract that processed the shipment or, without a contract, the carrier name |
| `data.carrier.tracking_number` | string \| null | always | Tracking number (AWB) at the carrier. It may come as `null`/empty before processing |
| `data.carrier.timeline` | array | always | All the events, in the order of recording: receipt, payment, processing and, after that, the carrier tracking events |
| `data.cost_center` | object | optional | Only appears when the shipment has a cost center |
| `data.cost_center.code` | integer | optional | Cost center code |
| `data.cost_center.name` | string \| null | optional | Cost center name |
| `data.received` | array | always | Receipt event (one item) |
| `data.processing_payment` or `data.paid_out` | array | always one of the two | Payment event (one item) |
| `data.processing_shipment` or `data.shipped` | array | after payment is approved or billed | Processing event at the carrier (one item) |
| `data.collecting`, `data.collected`, `data.in_transit`, `data.delivering`, `data.delivered` | array | according to tracking | Last carrier event in that status (one item) |
| `data.last_update` | object | optional | Current state. **It only appears** after the first carrier tracking event or when the shipment is in `cancelling`, `cancelled` or `error` |

Each event (in `timeline`, in the groups and in `last_update`) has the same shape:

| Field | Type | Format | Description |
|---|---|---|---|
| `update_date` | string | `AAAA-MM-DD` | Event date (YYYY-MM-DD) |
| `update_time` | string | `HH:MM:SS` | Event time. **Exception:** in the `processing_shipment` event, this field currently comes with the date (`AAAA-MM-DD`) instead of the time |
| `status_code` | string | - | Platform code (`XXX0001`) or raw code of the payment provider/carrier |
| `status_description` | string | - | Human-readable description. Translated by `lang` only in the events generated by the platform |

## Endpoint: query status by channel

- **Method and route:** `GET /v1/shipping/status/{channel_identifier_number}/{channel_code}`
- **When to use:** when you stored only the order identifier in your sales channel (informed in the quotation),
  and not the quotation UUID.

### Parameters

| Name | Location | Type | Required | Size | Default | Description |
|---|---|---|---|---|---|---|
| `channel_identifier_number` | path | string | **yes** | - | - | Order identifier in the channel, exactly as informed in the quotation |
| `channel_code` | path | integer | no | - | absent | Sales channel code informed in the quotation. It must be an integer |

> **How the search works:**
>
> - **With `channel_code`:** searches for the shipment whose quotation has this identifier **and** this channel code.
> - **Without `channel_code`:** searches **only** for shipments whose quotation was created **without** a channel code.
>   If your quotation had a `channel_code`, you need to send it.
> - **Cancelled shipments are not considered**. If there is more than one valid shipment, the most recent one applies.
> - To omit the `channel_code`, simply do not send the last segment. The value `,` is also treated as absent.

### Minimum payload

```
GET /v1/shipping/status/PED-2026-0001
```

### Maximum payload

```
GET /v1/shipping/status/PED-2026-0001/1
```

### Request example

```bash
curl --request GET \
  --url https://api.shipsmart.global/v1/shipping/status/PED-2026-0001/1 \
  --header 'Authorization: Bearer YOUR_TOKEN' \
  --header 'lang: pt'
```

### Response example

`200 OK` — same structure as [query status by shipment](#endpoint-query-status-by-shipment).

`422 Unprocessable Entity` — non-numeric `channel_code`:

```json
{
  "status": "warning",
  "message": "Oopss.. Algo inesperado aconteceu. Tente novamente mais tarde. Caso o erro persista, acione a equipe técnica!",
  "data": {
    "channel_code": [
      "O campo channel code deve conter um número inteiro."
    ]
  }
}
```

### Response fields

Identical to those of [query status by shipment](#response-fields).

## Business rules

- **Only shipments from your account.** The shipment must have been created by the token account. Shipments from another
  account respond `400` with `Nenhuma remessa encontrada com o código especificado!`.
- **Every shipment must have a payment record** for the status to be built. If there is none,
  the response is `404` with `Nenhuma entrada de pagamento foi registrada para esta remessa!` (fixed message,
  it does not change with `lang`).
- **Payment and displayed group:**

  | Shipment `payment.type` | Payment event | Processing event |
  |---|---|---|
  | `billed` | `processing_payment` with `PPY0001` | `processing_shipment` → `shipped` |
  | `gateway` | `processing_payment` (payment provider code) until approval; then `paid_out` | Only appears after `paid_out` |
  | `afterward` | `processing_payment` until the payment is approved | Only appears after the payment is approved |

  With `afterward`, the shipment may already have documents without the `shipped` group appearing. In this case, query
  [Shipment Documents](api-documentos.md) directly.
- The group changes from `processing_shipment` to `shipped` at the moment the **documents are generated**; the date
  and time of `shipped` are those of the generation of the first document.
- The tracking groups (`collecting` to `delivered`) only appear after the carrier starts sending events.
- When the shipment is in `cancelling`, `cancelled` or `error`, the `last_update` uses the platform own
  description (table [Descriptions generated by the platform](#descriptions-generated-by-the-platform)) instead of the raw
  carrier text.
- **Consolidation:** while the shipment is awaiting consolidation or being consolidated, the status query may
  respond `500`. Wait for the consolidation to finish and query again.
- **Automatic cancellation:** shipments that, **29 days after creation**, still do not have a tracking number at the
  carrier (and have not gone beyond `shipped`) may be cancelled automatically by the platform.
- **End of life cycle:** shipments older than **2 months** that have not reached a final state
  (`delivered`, `cancelled`, `foc` or `eol`) are closed by the platform and stop receiving updates.
- The search by AWB in this route considers the most recent shipment with that number.
- The query by channel **ignores cancelled shipments**: to follow a cancellation, query by `{shipping}`.

### Polling best practices

| Situation | Recommended interval |
|---|---|
| Right after creating the shipment (waiting for `shipped`) | 10 to 30 seconds, with backoff |
| Shipment already in `shipped`/`in_transit` | 1 to 4 hours |
| `last_update` in `delivered`, `cancelled`, `foc` or `eol` | Stop polling: these are final states |
| Shipment older than 2 months | Stop polling: the shipment no longer receives updates |

1. Read `data.last_update` to decide whether there was a change — it is the simplest view. Remember that it only
   exists after the first carrier event (or in cancellation/error); before that, use the groups.
2. Stop polling in the final states.
3. Use exponential backoff on `500`.
4. Treat `400`/`404` as a business condition: do not repeat the same request in a loop.

## Common errors

| Status | Meaning/Message | How to fix |
|---|---|---|
| `400` | `remessa.status.status_not_found: ` — no shipment found by the UUID or by the AWB (query by `{shipping}`; the message comes in this format, without translation). It also occurs when sending an NF-e key | Check the `{shipping}`. Use the quotation UUID or the AWB |
| `400` | `Nenhuma remessa encontrada com o código especificado!` — shipment from another account (by `{shipping}`) or no shipment found (by channel) | Check the identifier, the `channel_code` and the token used |
| `403` | `Has no permission!` | Ask support for the status query permission |
| `403` | `Usuário especificado encontra-se bloqueado em nosso sistema!` | Account blocked: contact support |
| `404` | `Nenhum usuário encontrado para o token especificado!` | Check the token sent in `Authorization` |
| `404` | `Nenhuma entrada de pagamento foi registrada para esta remessa!` | Wait for the payment to be recorded; if it persists, contact support |
| `422` | `O campo channel code deve conter um número inteiro.` (in `data.channel_code`) | Send an integer in `channel_code` or omit the segment |
| `500` | `Oopss.. Algo inesperado aconteceu ao buscar status da remessa. Tente novamente mais tarde. Caso o erro persista, acione a equipe técnica!` | Retry with backoff; if it persists, contact support |

## Final notes
- `data.carrier.timeline` is the most complete view; the groups are an operational summary to make
  programmatic reading easier.
- Store the `tracking_number` to offer the end customer tracking on the carrier website.
- To download the label and invoice as soon as the shipment reaches `shipped`, see
  [Shipment Documents](api-documentos.md).
- To create and cancel shipments, see [Shipment (v1)](api-remessa-v1.md) and [Shipment (v2)](api-remessa-v2.md).
- Consolidated list of error messages: [Error Codes](api-codigos-de-erro.md).
